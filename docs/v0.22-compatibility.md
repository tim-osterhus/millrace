# v0.22 Compatibility

Published v0.22.3 and the current private 0.22.4 candidate use store schema 11.
Published v0.22.2 workspaces use schema 8; schemas 8, 9 and 10 have no in-place
migration. Preserve existing state, finish or retire its work with the matching
runtime, and initialize a separate fresh candidate workspace.

Millrace v0.22 deliberately does not preserve the v0.21 runtime shape.
`Removed` means the old surface is not a v0.22 API. `Deferred` means the
surface is outside v0.22; no delivery date is implied.

| Surface | Disposition | v0.22 replacement or boundary |
| --- | --- | --- |

## Supported v0.22 Boundary

Published v0.22.3 retains the generic context contracts below but defers the
experimental LAD semantic-workspace profile from the official Plus package.
This is a workflow-distribution scope decision, not removal of generic context
support or a claim that the experiment established comparative efficacy. The
current private 0.22.4 candidate adds the explicitly selected Pi route described
below; it does not change this package boundary.
Run-scoped pause/resume is implemented for admitted unstarted runs and the
qualified surviving Millforge native owner/effect profile. Five seconds bounds
caller observation; a slow operation remains pending until quiescence is proved.
Selected-plan dispatch suspension remains a separate control. See
[Core control candidate](core-control-candidate.md) for exact authority, loss,
recovery and qualification boundaries.

v0.22 supports:

- compiler-validated workflow packages and immutable selected plans;
- durable local queues, runs, artifacts, waits, interventions, and traces;
- schema-11 durable daemon ceilings over wall time, accepted starts, and
  reviewed adapter-reported token evidence;
- generic compiler-validated context bindings and schema-3 immutable
  CAS-backed checkouts with durable root-state proofs, while schema-2 manifests
  remain byte-preserving inspect-only legacy; these checkouts are pinned to
  schema-2 runner sessions;
- schema-7 dispatch descriptors and Codex wrapper protocol 4 for bound
  navigation and reviewed usage, while unbound protocol-3 behavior remains
  byte-compatible;
- fail-closed checkout integrity and selected direct/protected writeback
  validation before runner evidence becomes workflow authority;
- explicit local operator commands;
- daemon execution through selected Millforge or Codex runner authority;
- bounded `--monitor basic` output;
- workflow package path, archive, and installed-distribution import/export;
- selected entrypoint and stage-core materialization from validated package
  bytes;
- selected fanout, join, recovery, quarantine, operator-wait, and completion
  behavior represented in compiled workflow data.

An absent legacy command normally produces the current parser or
`command_not_implemented` error. Authored compatibility profiles produce
`unsupported_compatibility_profile`. Unsupported selected adapter authority
can produce `adapter_kind_refused`. These are current refusal categories, not
migration facilities.

## Older Stores To Schema 11

Runner-session context and the current daemon persistence require store schema
11. The runtime does not initialize new tables over an existing
schema-version-6 or schema-version-7 database and performs no automatic migration.
Any command that recognizes an otherwise valid exact schema-6 or
schema-7 workspace returns `workspace_upgrade_required` with exit status 4.
The database, CAS, and runner-event sidecar remain byte-for-byte unchanged.

Schemas 8, 9 and 10 are not compatibility readers for schema 11: opening or
initializing an exact schema-8, schema-9 or schema-10 store returns the existing
unsupported-schema refusal without changing its bytes. Missing or malformed
metadata, versions below 6, and future or unknown schema versions keep their
existing unsupported/corrupt-state behavior; they are not misreported as the
exact upgrade boundary. A later one-shot migration would require a separate
reviewed contract.

Operators must finish or retire active v0.22 work with the v0.22 runtime.
Then initialize a new schema-11 workspace and re-admit current packages and
plans. No runner session or context manifest is inferred for an active
pre-session run.

## Current private 0.22.4 candidate

The coordinated Core, Plus, and meta source candidate targets unpublished 0.22.4.
Published v0.22.3 remains the public release. Monitor-retained predecessor Pi
artifacts keep their original identities: Core 0.22.4.dev6+pi.local01 and Plus
0.22.4.dev5+pi.local01. Their scripted-provider results do not qualify final
0.22.4 artifacts. Public v0.22.4 is held pending the real-model Campaign Monitor
and final release checks.

The private Pi workflow opts into a component-free pi_rpc binding. Pi completion
selects Core's packaged payload-capacity contract through nested runner-binding
schema 4. Store schema 11, selected-plan schema 18, dispatch schema 7,
runner-session schema 2, and context-manifest schema 3 remain in use; there is
no store or session-schema migration. Existing unsupported-schema refusals
remain in force.

The foreground profile uses the pinned v2 trusted per-command POSIX-group
observer. Retained predecessor artifacts have installed scripted-provider
evidence on Darwin and one pinned Ubuntu 24.04 x86_64 installation; the Linux
run includes one five-stage LAD route. This does not qualify final 0.22.4
artifacts, every LAD stage, or a real model. The observer qualifies only its
covered process groups: escaped descendants and remote work are outside the
guarantee. Uncertain evidence refuses workflow-result application and may leave
orphan_risk. Pi reconciliation, active native controls, and owner-loss
reattachment are unsupported. Production provider token accounting remains
unqualified. See [Pi runner](pi-runner.md) for the pinned profile and its limits.
