# Blueprint Effect Behavior Matrix

This note records the current Blueprint runtime-effect behavior before the
declarative runtime effect migration. The source of truth for actual mutation is
still `src/millrace_ai/runtime/blueprint_effects.py`, dispatched by
`src/millrace_ai/runtime/effect_execution.py`. The declared policy lives in
`src/millrace_ai/assets/registry/runtime_effect_rules/blueprint_effect_rules.json`
and handler metadata lives in
`src/millrace_ai/assets/registry/runtime_effect_handlers/default_effect_handlers.json`.

The goal of this matrix is characterization, not redesign. Behaviors marked as
missing direct tests should be covered by parity tests before replacing the
legacy Python handler with declarative operations.

## Summary

| Effect | Safest migration order | Current characterization state |
| --- | ---: | --- |
| `manager_blueprint_manifest_to_blueprint_drafts` | 1 | Strong direct coverage for success, duplicates, replay, lifecycle invalid, and partial write. |
| `contractor_blueprint_candidate_persist` | 2 | Good direct coverage for success, equivalent replay, and duplicate conflicts. Partial mutation is not directly tested. |
| `evaluator_blueprint_rejected_to_draft_revision` | 3 | Happy-path and critique artifact selection are covered. Duplicate, replay, and partial mutation behavior need direct blockers before migration. |
| `evaluator_blueprint_approved_to_task` | 4 | Strong direct coverage for success, replay, duplicate conflicts, task parsing, and runtime partial-mutation policy. Direct handler partial-write injection is still missing. |
| `mechanic_blueprint_repair_apply` | 5 | Success and repair validation are covered. Duplicate/replay and partial mutation behavior are inherited from approval but need direct repair-specific parity tests. |

## `manager_blueprint_manifest_to_blueprint_drafts`

| Field | Current behavior |
| --- | --- |
| Declared effect-rule policy | Source `manager_blueprint`; outcome `MANAGER_BLUEPRINT_COMPLETE`; required artifacts `blueprint_manifest`, `blueprint_drafts`; destination family `blueprint_draft`; creates work items; duplicate policy `fail`; partial commit policy `block_source`; replay policy `resume_idempotently`; lineage policy `preserve_root`; lifecycle mutation plan `complete_spec_source_after_blueprint_effect`. Declared capabilities include equivalent manifest replay, legacy manifest identity replay, equivalent draft replay, duplicate manifest id, and duplicate draft id. |
| Actual source behavior | Reads `blueprint_manifest.json` and `blueprint_drafts.json` with Manager-specific failure classes for missing, parse, and schema errors. Validates manifest source kind/id against the active source, draft order against manifest ids, draft count, contiguous one-based indexes, strict previous-draft dependencies, and draft manifest/root/source identity. It checks equivalent existing outputs before requiring the source to be active. It writes the manifest, enqueues missing drafts, and returns `request_complete_source` with a complete lifecycle intent for spec or incident sources. |
| Duplicate behavior | Existing manifest id must be equivalent after resolving canonical and legacy/root-keyed manifest entries, otherwise `blueprint_manifest_duplicate`. Existing draft id is scanned across queue, active, approved, blocked, canceled, and superseded states. Draft comparison ignores status, current revision, latest blueprint id, latest critique id, and updated_at. Divergent or multi-state draft entries fail with `blueprint_draft_duplicate`. |
| Idempotent replay behavior | If the manifest and all drafts already exist equivalently and the source is active, the handler returns success with a complete lifecycle intent. If they already exist and the source is already in the target state, it returns success with no lifecycle intent and no created paths. If only some equivalent outputs exist and the source is active, it writes the missing outputs and completes the source. Progressed draft state is accepted by the draft identity comparison. |
| Partial mutation behavior | Tracks created paths for manifest and draft writes. Write failures after any created path return `blueprint_partial_mutation`, `partial_mutation`, block lifecycle intent, and `request_block_source`. Pre-write duplicate write races map to manifest or draft duplicate where recognizable; otherwise they conservatively map to partial mutation. |
| Failure policy integration | Runtime failure policies explicitly cover Manager artifact failures, duplicate/lifecycle-invalid pre-mutation conservative blocks, and Manager partial mutation conservative blocks. Unclassified pre-mutation failures fall to default runtime repair. |
| Repair behavior | The handler itself does not apply repair. Default runtime repair may route unclassified pre-mutation failures to `mechanic_blueprint`. `BlueprintRepairDecisionDocument` also accepts a Manager rerun action, but `mechanic_blueprint_repair_apply` does not apply that action. |
| Exact tests that currently cover it | `tests/blueprint/test_effects.py::test_manager_manifest_promotion_enqueues_drafts_and_returns_source_complete_intent`; `test_manager_manifest_promotion_classifies_artifact_failures_precisely`; `test_manager_manifest_promotion_classifies_manifest_draft_mismatch`; `test_manager_manifest_promotion_classifies_duplicate_manifest_id`; `test_manager_manifest_promotion_classifies_duplicate_draft_id`; `test_manager_manifest_promotion_replay_after_source_done_is_noop_success`; `test_manager_manifest_promotion_replay_accepts_progressed_draft_state`; `test_manager_manifest_promotion_replay_after_incident_resolved_is_noop_success`; `test_manager_manifest_promotion_maps_artifact_read_failure`; `test_manager_manifest_promotion_finishes_partial_replay_when_outputs_match`; `test_manager_manifest_promotion_reports_source_lifecycle_invalid_after_validation`; `test_manager_partial_write_failure_requests_source_blockage`; `tests/runtime/test_runtime_effects.py::test_manager_blueprint_malformed_artifact_routes_through_runtime_failure_policy`; `test_manager_blueprint_conservative_failure_policy_blocks_and_annotates`; `test_manager_blueprint_partial_mutation_policy_blocks_without_model_repair`; `test_unclassified_pre_mutation_effect_failure_routes_to_default_repair`; `test_default_runtime_effect_repair_blocks_after_threshold`; `test_runtime_effect_require_operator_policy_blocks_with_operator_visible_reason_and_event`; `tests/integration/test_blueprint_planning_loop.py::test_blueprint_mode_approval_path_promotes_two_strict_sequence_drafts_and_closes`; `test_blueprint_same_root_arbiter_remediation_uses_distinct_manifest_identity`. |
| Missing direct tests | No blocking Manager direct-test gap for first migration. Future parity should still compare legacy vs declarative results for success, duplicate manifest, duplicate draft, invalid lifecycle, equivalent replay after completion, and partial write. |

## `contractor_blueprint_candidate_persist`

| Field | Current behavior |
| --- | --- |
| Declared effect-rule policy | Source `contractor_blueprint`; outcome `BLUEPRINT_CANDIDATE_READY`; required artifacts `blueprint_packet`, `blueprint_markdown`; creates no work items; duplicate policy `fail`; partial commit policy `block_source`; replay policy `resume_idempotently`; lineage policy `preserve_root`; no lifecycle mutation plan. Declared capabilities include equivalent candidate replay and same-id candidate duplicates. |
| Actual source behavior | Requires an active `blueprint_draft` source. Reads `blueprint_packet.json`, validates it matches the active draft, and requires references to include the latest open critique when the draft has `latest_critique_id`. It validates or writes the candidate packet and markdown sidecar under `blueprints/packets/candidates/`, then updates the active draft with `latest_blueprint_id`. It returns `continue_route` and no lifecycle intent. |
| Duplicate behavior | Existing candidate packet with the same `blueprint_id` must be model-equivalent or the handler returns `blueprint_candidate_duplicate_conflict`. Existing candidate markdown must be newline-normalized equivalent to run `blueprint.md` or the handler returns `blueprint_candidate_markdown_conflict`. |
| Idempotent replay behavior | If both packet and markdown exist equivalently, the handler writes no artifact and still updates the active draft pointer. If one equivalent output exists, it writes the missing counterpart and updates the draft. |
| Partial mutation behavior | Tracks packet and markdown created paths. Any `_ContractorBlueprintEffectError` returns its stable class; other exceptions return `blueprint_partial_mutation` if any path was created, otherwise `blueprint_candidate_invalid`. Draft update happens after durable writes, so a draft update failure after packet/markdown creation is reported as partial mutation. |
| Failure policy integration | No Contractor-specific runtime failure policy is declared. Pre-mutation failures are eligible for the default runtime repair route only if the generic runtime repair conditions apply. Partial mutations block conservatively because default repair only considers pre-mutation failures. |
| Repair behavior | No explicit repair-apply path. Rejection revisions may later cause the Contractor to emit a revised candidate that references the latest open critique. |
| Exact tests that currently cover it | `tests/blueprint/test_effects.py::test_contractor_candidate_persistence_updates_active_draft_after_durable_writes`; `test_contractor_candidate_replay_accepts_existing_equivalent_outputs_and_updates_draft`; `test_contractor_candidate_replay_reconciles_existing_equivalent_packet`; `test_contractor_candidate_replay_reconciles_existing_equivalent_markdown`; `test_contractor_candidate_replay_blocks_divergent_packet_conflict`; `test_contractor_candidate_replay_blocks_divergent_markdown_conflict`; `tests/integration/test_blueprint_planning_loop.py::test_blueprint_mode_approval_path_promotes_two_strict_sequence_drafts_and_closes`; `test_blueprint_mode_rejection_cycle_returns_to_contractor_before_approval`; `test_blueprint_approval_generated_task_invalid_recovers_without_duplicate_candidate`. |
| Missing direct tests | Missing direct coverage for latest-critique reference enforcement, missing/malformed packet and missing markdown classification, and partial mutation after packet or markdown creation, especially draft update failure after durable writes. |

## `evaluator_blueprint_approved_to_task`

| Field | Current behavior |
| --- | --- |
| Declared effect-rule policy | Source `evaluator_blueprint`; outcome `BLUEPRINT_APPROVED`; required artifacts `blueprint_evaluation`, `generated_task`; destination family `task`; creates work items; duplicate policy `fail`; partial commit policy `block_source`; replay policy `resume_idempotently`; lineage policy `preserve_root`; lifecycle mutation plan `approve_blueprint_draft_after_effect`. Declared capabilities include equivalent approval replay and generated task same-id duplicates. |
| Actual source behavior | Accepts an active or already approved `blueprint_draft` source, but fails if both states contain the draft. Resolves the latest packet from candidates or approved and requires equivalent content if both exist. Reads approved evaluation, validates it matches the packet, resolves `generated_task` through artifact contracts, validates generated task root lineage, spec id, acceptance, required checks, and target scope. Promotion adds approved packet and evaluation references to the queued task. |
| Duplicate behavior | Existing evaluation, approved packet, generated task, and promotion records must be equivalent. Existing generated task is scanned in queue, active, done, and blocked task states; multiple entries or divergent content return `blueprint_task_duplicate`. Approved markdown must be newline-normalized equivalent to candidate markdown or run `blueprint.md`, otherwise `blueprint_approved_markdown_conflict`. |
| Idempotent replay behavior | Complete approved state replays as success with no created paths and no lifecycle intent when the draft is already approved. Equivalent partially promoted state can create only missing records, such as a missing promotion, and still complete the active draft. Canonical `generated_task.json` is preferred over invalid markdown; malformed canonical JSON blocks before markdown fallback. |
| Partial mutation behavior | Promotion writes in this order: evaluation, move candidate packet to approved, move candidate markdown to approved, enqueue task, persist promotion. Created paths are appended for each durable mutation. Later exceptions map to `blueprint_partial_mutation`; otherwise failure classes are mapped from generated task artifact errors, validation errors, task duplicates, and evaluation invalidity. Move operations are recorded only as created destination paths, not as moved-from paths. |
| Failure policy integration | `blueprint_approval_pre_mutation_effect_validation` routes pre-mutation `generated_task_missing` and `generated_task_invalid` failures for `evaluator_blueprint_approved_to_task` to `mechanic_blueprint`. Partial mutation and duplicate conflicts block through the normal effect result path because there is no approval-specific partial policy. Runtime also normalizes a failure with created paths from pre-mutation to partial mutation. |
| Repair behavior | Failed pre-mutation generated task validation is repaired by `mechanic_blueprint_repair_apply`, which validates the failure context and applies the same promotion helper with `repaired_generated_task`. |
| Exact tests that currently cover it | `tests/blueprint/test_effects.py::test_evaluator_approval_enqueues_one_task_and_returns_draft_approval_intent`; `test_evaluator_approval_replays_complete_approved_state_without_duplicate_writes`; `test_evaluator_approval_replays_equivalent_generated_task_before_promotion`; `test_evaluator_approval_replay_blocks_missing_approved_markdown_when_candidate_missing`; `test_evaluator_approval_replay_blocks_divergent_approved_markdown_after_approved_draft`; `test_evaluator_approval_replay_blocks_divergent_approved_markdown_without_candidate`; `test_evaluator_approval_replay_blocks_divergent_evaluation_collision`; `test_evaluator_approval_replay_blocks_divergent_approved_packet_collision`; `test_evaluator_approval_replay_blocks_divergent_generated_task_collision`; `test_evaluator_approval_replay_blocks_divergent_promotion_collision`; `test_evaluator_approval_uses_canonical_generated_task_json_when_markdown_is_invalid`; `test_evaluator_approval_fails_malformed_canonical_generated_task_json_before_fallback`; `tests/runtime/test_runtime_effects.py::test_pre_mutation_effect_failure_routes_through_runtime_failure_policy`; `test_partial_mutation_effect_failure_blocks_source_conservatively`; `test_effect_failure_with_created_paths_cannot_route_as_pre_mutation`; `tests/integration/test_blueprint_planning_loop.py::test_blueprint_mode_approval_path_promotes_two_strict_sequence_drafts_and_closes`; `test_blueprint_approval_generated_task_invalid_recovers_without_duplicate_candidate`. |

## `evaluator_blueprint_rejected_to_draft_revision`

| Field | Current behavior |
| --- | --- |
| Declared effect-rule policy | Source `evaluator_blueprint`; outcome `BLUEPRINT_REJECTED`; required artifacts `blueprint_evaluation`, `blueprint_critique`; creates no work items; duplicate policy `fail`; partial commit policy `block_source`; replay policy `resume_idempotently`; lineage policy `preserve_root`; no lifecycle mutation plan. Declared capabilities include equivalent rejection replay and same-id rejection duplicates. |
| Actual source behavior | Requires an active `blueprint_draft`, reads the latest candidate packet, reads rejected evaluation, resolves `blueprint_critique` through artifact contracts including the legacy `critique_packet.json` filename, and validates evaluation/critique/packet lineage plus matching `critique_id`. It persists the evaluation, moves the candidate packet to rejected, moves candidate markdown to rejected when present, persists an open critique, and updates the active draft with `current_revision`, `latest_critique_id`, `latest_blueprint_id`, and `updated_at`. It returns `continue_route` and no lifecycle intent. |
| Duplicate behavior | Despite the declared duplicate and replay capabilities, the current handler does not preflight equivalent existing evaluation, rejected packet, rejected markdown, or critique records. Existing destinations fail through `QueueStateError` or unique-write errors. Because all exceptions are collapsed by the top-level handler, duplicate classes generally surface as `blueprint_critique_invalid` before mutation or `blueprint_partial_mutation` after any created path. |
| Idempotent replay behavior | Not effectively idempotent today. After a successful rejection, replay cannot find the candidate packet because it has been moved to rejected, so the handler blocks before mutation with `blueprint_critique_invalid`. If partial outputs exist while the candidate remains, unique-write and move collisions block rather than reconcile. |
| Partial mutation behavior | Created paths are appended for evaluation write, rejected packet destination, rejected markdown destination, and critique write. Active draft update happens last. Any exception after the first created path returns `blueprint_partial_mutation`. Move operations are recorded only as destination created paths, not as moved-from paths. |
| Failure policy integration | No rejection-specific runtime failure policy is declared. Pre-mutation failures can reach default runtime repair if generic conditions apply; partial mutations block conservatively. |
| Repair behavior | No explicit repair-apply path. The intended workflow is route continuity back to Contractor for a revised candidate while the draft remains active with critique context. |
| Exact tests that currently cover it | `tests/blueprint/test_effects.py::test_evaluator_rejection_persists_critique_and_keeps_active_draft`; `test_evaluator_rejection_uses_canonical_blueprint_critique_json_without_legacy_packet`; `test_evaluator_rejection_fails_malformed_canonical_critique_before_legacy_fallback`; `tests/integration/test_blueprint_planning_loop.py::test_blueprint_mode_rejection_cycle_returns_to_contractor_before_approval`. |
| Missing direct tests | Blocking gap before migration: direct tests for replay after successful rejection, duplicate evaluation id, duplicate rejected packet, duplicate critique id, missing candidate markdown behavior, partial mutation after evaluation write, partial mutation after packet/markdown move, and active draft update failure after durable writes. The declared replay policy currently does not match the source behavior and should be classified before migration. |

Handler metadata allows source families `spec`, `incident`, and `blueprint_draft`, but the implementation requires `blueprint_draft` for the promotion path. |

| Duplicate behavior | Duplicate behavior is inherited from the approval promotion helper: evaluation, approved packet, approved markdown, generated task, and promotion must be equivalent; divergent duplicates return approval conflict classes unless caught and remapped. Repair-decision duplicates are not a durable store concept in this handler. |
| Idempotent replay behavior | Equivalent already-promoted state should replay like approval promotion because the helper accepts approved draft/packet state and equivalent outputs. This is not directly tested for the repair handler. Repair context still must match the failed stage result and repair decision on every replay. |
| Partial mutation behavior | Uses the approval helper write order and created-path tracking. `_RepairBlueprintEffectError` failures keep repair-specific classes. `_ApprovalBlueprintEffectError` or other exceptions after created paths return `blueprint_partial_mutation`; before created paths they are remapped to `blueprint_repair_context_mismatch`. |
| Failure policy integration | No failure policy currently routes failures from `mechanic_blueprint_repair_apply`. Its failures block through the normal runtime effect result path. It is the target of the approval generated-task failure policy. |
| Repair behavior | This is the packaged repair application path for approval generated-task failures. It can promote a repaired generated task and approve the draft. It does not implement Manager rerun or operator-review actions beyond returning `blueprint_repair_requested_operator`. |

| Missing direct tests | Blocking gap before migration: repair-specific replay after successful promotion, divergent duplicate evaluation/packet/task/promotion behavior through the mechanic handler, missing repaired task, `block_for_operator`, unsupported repair action, missing failed stage-result context, and partial mutation after delegated approval writes. |

## Migration Notes

`manager_blueprint_manifest_to_blueprint_drafts` is the safest first migration.
It is conceptually the smallest multi-write effect, already has strong direct
coverage for duplicate and replay behavior, and exercises the core primitives a
declarative operation needs first: artifact parsing, collection validation,
equivalent-output checks, durable store writes, enqueue-many, and source
lifecycle intent.

The main policy mismatch to resolve before later migrations is
`evaluator_blueprint_rejected_to_draft_revision`: its rule declares duplicate
fail and idempotent replay, but the implementation currently does not preflight
equivalent rejection outputs and does not replay successfully after moving the
candidate packet.
